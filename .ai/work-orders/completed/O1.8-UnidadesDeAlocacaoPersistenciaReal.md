## Plano de implementação

Domain/Application/Infrastructure/Api de `UnidadeAlocacao`, replicando fielmente o padrão físico de `Usuario`
(O1.6) — entidade com construtor de fábrica e mutadores controlados (`Atualizar`/`Ativar`/`Inativar`),
sem exclusão física, escopada por `UnidadeNegocioId`. EF Core Configuration + migration própria. Casos de uso
(Listar/Obter/Criar/Atualizar/AlterarStatus) seguindo o padrão de `IUsuarioUseCases`. Endpoint HTTP protegido
pela permissão já reservada `UnidadeAlocacao.Gerenciar` (RBAC real, O1.5), com escopo por Unidade de Negócio
resolvido exclusivamente da sessão autenticada — nunca do payload. Frontend convertido de
`unidadesAlocacaoMockApi.ts` para um cliente HTTP real, seguindo o padrão de `centrosCustoApi.ts` (O1.7).

## Relatório final

**Concluída em 11/08/2026.**

- **Backend:** `UnidadeAlocacao` (Domain), `UnidadeAlocacaoConfiguration` (EF Core), `IUnidadeAlocacaoRepository`/
  `UnidadeAlocacaoRepository`, casos de uso `Listar/Obter/Criar/Atualizar/AlterarStatusUnidadeAlocacaoUseCase`,
  `UnidadesAlocacaoController` (endpoints REST protegidos por `UnidadeAlocacao.Gerenciar`, CSRF header filter,
  escopo por Unidade de Negócio da sessão). Sem vínculo com Centro de Custo (fora de escopo, O1.9) e sem
  integração ERP (ADR-0020, item 4).
- **Migration:** `AddUnidadeAlocacaoO18` (EF Core) — `CREATE TABLE UnidadesAlocacao` + índice único
  `(UnidadeNegocioId, Nome)`. Aditiva, sem exclusão de dados. Gerada via `dotnet ef migrations add` real e
  aplicada ao banco de desenvolvimento via `dotnet ef database update` (ambiente com conectividade disponível
  nesta sessão).
- **Testes:** `UnidadeAlocacaoUseCasesTests` (13 testes novos: criação, unicidade por Unidade de Negócio,
  isolamento cross-BU, ativação/inativação, listagem escopada). Suíte completa do backend: **512/512 testes
  unitários** e **7/7 testes de integração** aprovados (nenhuma regressão em Usuários/Perfis/Centros de Custo).

  HTTP real); `unidadesAlocacaoMockApi.ts` removido. Campo "Unidade de Negócio" removido do formulário — é
  sempre resolvido pelo backend a partir da sessão, nunca escolhido pelo cliente (mesmo padrão de Usuário/
  Perfil), correção necessária identificada durante a conversão, não um redesign. Estados de loading/erro/
  vazio/acesso negado (401/403) preservados no mesmo padrão visual AZZAS/SOMA. Suíte de testes de frontend
  reescrita para interceptar `fetch` real (mesmo padrão de `CentrosCustoPage.test.tsx`, O1.7): **72/72 testes**
