# Work Order — O1.13.5 — Fundação dos Agents Especialistas Linx (Conhecimento ERP/Banco)

- Fase: Onda 1 — Fundação Funcional
- Status: ✅ Concluída (aberta e encerrada formalmente em 11/08/2026)
- Dependências: nenhuma bloqueante; paralelizável a O1.10–O1.13; deve concluir antes do fechamento formal da O1.14 (consolidação do blueprint), mas não é dependência dura dela
- Data de aprovação: 11/08/2026 (Product Owner)
- Origem: decisão do Product Owner registrada na sessão de execução da O1.10 (11/08/2026) — ver `.ai/BACKLOG.md`, seção "Planejamento dos Agents Especialistas Linx"

## Objetivo

Estabelecer a fundação arquitetural — não a implementação operacional completa — para dois Agents especialistas
no ERP Visual Linx: **Linx ERP Specialist** (conhecimento funcional/técnico do ERP) e **Linx Database
Specialist** (conhecimento estrutural do banco `SOMA_DESENV`), com memória persistente, versionada e
recuperável, e proveniência explícita do conhecimento armazenado (Descoberto/Inferido/Validado/Aprovado).

## Contexto

Nenhuma das Work Orders O1.10–O1.14 tem escopo natural para esta fundação (ver análise em `.ai/BACKLOG.md`).
As integrações ERP mais profundas com Item e Pedido pertencem a Ondas futuras (O1.12 exclui explicitamente
"regras de negócio de orçamento por processo de compra" para a Onda 3; O1.13 exclui explicitamente
integrações que "ainda não existem" para a Onda 4) — esta fundação antecipa a base de conhecimento que essas
integrações futuras vão precisar, sem antecipar as próprias integrações.

## Escopo

- Domain/Application/Infrastructure/Api de uma base de conhecimento persistente (`LinxKnowledgeEntry` ou
  equivalente): categoria (schema de tabela/coluna, regra funcional, fluxo do ERP, integração, histórico de
  decisão), conteúdo, proveniência (Descoberto/Inferido/Validado/Aprovado), fonte, autor/ator, versionamento
  temporal (nunca sobrescrita silenciosa — nova versão, histórico preservado).
- Mecanismo de recuperação (busca textual/estruturada como MVP; arquitetura preparada para evoluir a
  embeddings/RAG mais sofisticado sem redesenho).
- Persistência real em SQL Server (mesma stack, mesmo padrão físico dos demais módulos administrativos).
- Definição dos dois papéis de Agent (Linx ERP Specialist, Linx Database Specialist) como consumidores/
  produtores dessa base — prompts e ferramentas de consulta, não um motor de aprendizagem que altera pesos
  de modelo.
- Acesso READ-ONLY controlado ao `SOMA_DESENV` para descoberta, reaproveitando o padrão de introspecção
  dinâmica de schema já existente em `SomaFornecedorReader`/`SomaFilialReader`/`SomaCentroCustoReader`.
- RBAC real: permissão dedicada para quem pode registrar/promover conhecimento a "Aprovado".

## Fora de escopo

- Execução autônoma de SQL arbitrário (INSERT/UPDATE/DELETE/ALTER/DROP) pelo Agent em qualquer ambiente,
  especialmente produção — nunca permitido, nesta ou em nenhuma Work Order futura sem governança própria
  dedicada.
- Integração operacional de Fornecedor/Item/Pedido com o Linx usando esses Agents (Ondas 3/4).
- Ingestão em massa dos +300 arquivos `obj_*.prg`/documentação Linx — apenas a estrutura capaz de receber
  esse conteúdo no futuro.
- Qualquer alteração de pesos/fine-tuning de modelo ("aprendizado" aqui significa conhecimento persistido,
  versionado e recuperável — nunca alteração do modelo em si).

Domain/Application/Infrastructure/Api de Knowledge, seguindo o padrão físico dos demais módulos
administrativos (EF Core, migrations, RBAC real). Leitor read-only do `SOMA_DESENV` reaproveitando a
introspecção dinâmica já validada em B2.1/O1.7.

## Banco

## Plano de implementação

Auditoria prévia (Explore agent) confirmou: runtime de Agents (`IAgent`/`BaseAgent`/`AgentFactory`) e módulo
`Knowledge` genérico (`IKnowledgeService`/`MarkdownKnowledgeProvider`) já existentes, mas sem persistência
SQL/proveniência/versionamento — reaproveitados como padrão de referência (`KnowledgeAgent`), não
duplicados. `SomaFornecedorReader`/`SomaFilialReader`/`SomaCentroCustoReader` confirmados como o padrão
exato de introspecção dinâmica read-only a reaproveitar para a descoberta de schema Linx.

Implementado (Domain/Application/Infrastructure/Api, mesmo padrão físico dos módulos administrativos):

- `Domain.Knowledge.Linx`: `LinxKnowledgeEntry` (agregado versionado), `LinxEspecialista`,
  `LinxConhecimentoCategoria`, `LinxConhecimentoProveniencia`. Máquina de estados de proveniência
  (Descoberto/Inferido → Validado → Aprovado) e versionamento imutável (nova linha, nunca sobrescrita) no
  próprio agregado.
- `Application.Knowledge.Linx`: `IRegistrarConhecimentoUseCase` (com detecção de conflito contra versão
  já Validada/Aprovada), `IPromoverConhecimentoUseCase`, `IBuscarConhecimentoUseCase`,
  `IObterHistoricoConhecimentoUseCase`, `ILinxKnowledgeRepository`; `LinxErpSpecialistAgent`/
  `LinxDatabaseSpecialistAgent` (subclasses de `BaseAgent`, injetadas via DI — não pelo `AgentFactory`
  reflection-based, que só reconhece `IKnowledgeService`).
- `Infrastructure`: `LinxKnowledgeRepository` (EF Core), `LinxKnowledgeEntryConfiguration`,
  `LinxSchemaDiscoveryReader`/`ILinxSchemaDiscoveryReader` (introspecção read-only de `SOMA_DESENV`, mesmo
  padrão de guarda de banco/timeout dos readers existentes). Migration `AddLinxKnowledgeO1135` (aditiva:
  1 tabela nova + 2 permissões novas).
- `Api`: `LinxKnowledgeController` (busca/histórico exigem apenas autenticação; registrar/validar exigem
  `ConhecimentoLinx.Gerenciar`; a promoção final a "Aprovado" exige a permissão DEDICADA
  `ConhecimentoLinx.Aprovar`, nunca concedida implicitamente por quem registra/valida).

## Relatório final

**Objetivo alcançado:** fundação arquitetural (não implementação operacional completa) dos dois Agents
Especialistas Linx, com memória persistente versionada e proveniência explícita.

**Segurança (self-review):** 0 CRITICAL, 0 HIGH. Cobertura: acesso ao ERP estritamente read-only por
construção de contrato (nenhum método de escrita exposto — comprovado por teste de reflexão, não apenas por
convenção); nenhum SQL arbitrário (apenas `INFORMATION_SCHEMA` parametrizado); RBAC dedicado protegendo
"Aprovado" (não a mesma permissão de quem registra/valida); Agent nunca se autoatribui aprovação (não existe
caminho de código do Agent até o caso de uso de promoção — apenas humanos autenticados via o endpoint
protegido); conteúdo persistido tratado como dado citado no prompt, nunca como instrução de sistema
(testado explicitamente contra um payload de prompt injection); isolamento cross-BU (`UnidadeNegocioId`
nulo = global, nunca vaza entre BUs); limites de tamanho (conteúdo 8000 chars, resultados de busca
1–200) contra consultas/persistência ilimitadas; nenhum secret logado (apenas nomes de schema/tabela).

**Validação funcional dos dois especialistas:** demonstrada com componentes reais (não apenas fakes) —
descoberta → persistência (EF Core) → consulta posterior → resposta do Agent citando proveniência e fonte
explícitas, para os dois papéis (`LinxDatabaseSpecialistAgent`/`LinxErpSpecialistAgent`).

**Testes:** backend 626 → 682 testes unitários (+56), 7 integração (inalterado) — 689/689 aprovados.
`dotnet build`: 0 erros, 0 avisos. Frontend não alterado nesta sprint (fundação é backend/arquitetural) —
suíte de 116 testes permanece válida sem necessidade de nova execução.

**Persistência:** migration `AddLinxKnowledgeO1135` gerada via `dotnet ef migrations add` real, aditiva
(1 tabela nova `LinxConhecimentoEntradas` + 2 permissões novas no catálogo RBAC), `has-pending-model-changes`
limpo, **aplicada ao banco de desenvolvimento** (`MaisCompras`, via `dotnet ef database update`).

**Chrome/MCP:** dispensado — sprint majoritariamente backend/arquitetural, sem frontend administrativo
nesta etapa (não exigido pela Work Order); cobertura automatizada suficiente para os critérios de aceite.

**Dívidas/evoluções futuras registradas (não bloqueantes):** evolução da busca textual/estruturada para
embeddings/RAG (ponto de extensão já isolado detrás de `IBuscarConhecimentoUseCase`, sem exigir redesenho);
ingestão dos +300 `obj_*.prg`/documentação Linx (fora de escopo, apenas a estrutura já comporta); frontend
administrativo mínimo de consulta/validação/aprovação de conhecimento (não exigido pelos critérios de
aceite desta Work Order); extração de um helper comum de conexão/guarda `SOMA_DESENV` compartilhado entre
`SomaFilialReader`/`SomaCentroCustoReader`/`LinxSchemaDiscoveryReader` (hoje duplicado 3x, oportunidade de
refatoração registrada, não corrigida por não ser exigida pelos critérios desta sprint).

**Impacto nos 41 entregáveis da Onda 1 / progresso técnico:** nenhum dos 41 entregáveis oficiais corresponde
diretamente a esta fundação (decisão já registrada em `.ai/BACKLOG.md`, "Planejamento dos Agents
Especialistas Linx") — percentual técnico da Onda 1 permanece inalterado (28/41 Concluído, 68,29% exato,
exibido 68%; MVP Global permanece 40,66% exato, exibido 41%). Registrada como entrega arquitetural
adicional da Onda 1, sem alterar o denominador 41 e sem executar `[atualizar dashboard]` (instrução
