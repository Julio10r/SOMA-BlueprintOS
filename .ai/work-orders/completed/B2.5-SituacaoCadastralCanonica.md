## Relatório final

**Divergência de escopo identificada e resolvida antes da implementação:** o rascunho original desta Work Order (acima) previa "adicionar campo persistido `SituacaoCadastral`/`DataSituacaoCadastral` em `Fornecedor`". A instrução de execução detalhada desta sessão (autorizada explicitamente pelo Product Owner) redefiniu o escopo real da B2.5 como contrato canônico + serialização + tipagem/apresentação — sem qualquer persistência nova em `Fornecedor` — e a seção 15 dessa instrução afirmava explicitamente "a expectativa é que B2.5 NÃO precise de migration". Nenhuma migration foi criada, nenhum campo novo foi persistido em `Fornecedor`. Este desvio do rascunho original é registrado aqui por transparência; a persistência de situação cadastral no cadastro do fornecedor, se necessária, é candidata a uma Work Order futura.

**Investigação do contrato atual (antes de qualquer alteração):**
- `SituacaoCadastralCnpj` estava definida em `ConsultaCnpjResultado.cs` com 5 valores: `Ativa, Baixada, Suspensa, Inapta, NaoEncontrada`. `NaoEncontrada` estava sobrecarregada: usada tanto como fallback de texto não reconhecido do provider quanto como valor "placeholder" obrigatório em toda falha de consulta (`CriarFalha`), mesmo falhas que nada têm a ver com "não encontrado" (timeout, erro interno, etc.).
- `BrasilApiCnpjProvider.MapSituacao` já usava exclusivamente `descricao_situacao_cadastral` (texto), nunca o código numérico `situacao_cadastral` — o código numérico do provider nunca atravessou o Adapter.
- **Achado crítico confirmado por teste empírico:** nenhum `JsonStringEnumConverter` estava registrado em nenhum lugar do backend (`Program.cs` usava apenas `AddOpenApi`/`AddHttpContextAccessor`, sem `ConfigureHttpJsonOptions`). Isso significa que **todo enum (`SituacaoCadastralCnpj`, `TipoErroConsultaCnpj`, `StatusConsultaCnpj`) estava sendo serializado pela API como o inteiro subjacente** (ex.: `situacaoCadastral: 0`), nunca como string — apesar do contrato TypeScript e de múltiplos componentes de frontend (`StatusBadge.tsx`, `ApprovalPanel.tsx`, `CadastroFornecedor.tsx`) já assumirem/compararem strings PascalCase (`"Ativa"`, `"Baixada"`, `"CnpjInvalido"`). Esta é a causa raiz estrutural do crash `value.toLowerCase is not a function` registrado no Design Review — o valor numérico bruto do enum, não um valor específico da BrasilAPI, atravessava até o `StatusBadge`.
- `StatusBadge.tsx` (genérico, compartilhado com Administração — Filial/Centro de Custo/Perfil/Usuário/etc. via `tone="situacao"` para Ativo/Inativo) derivava a classe CSS via `` `status-${value.toLowerCase()}` ``, assumindo `value` sempre string — sem nenhuma garantia estrutural disso para a situação cadastral do CNPJ.
- `linxSupplierContract.ts` tipava `SituacaoCadastralCnpj` como `"Ativa" | "Baixada" | "Suspensa" | "Inapta" | "NaoEncontrada" | string` — o `| string` final tornava o union praticamente aberto, permitindo qualquer string (e, por erro de tipagem, não protegia contra `number` em runtime).
- Nenhum outro call-site fazia cast, comparação numérica ou fallback silencioso sobre situação cadastral, além do já descrito.

**Representação canônica final** (`SituacaoCadastralCnpj`, Application layer, mesmo enum reaproveitado — nenhum segundo conceito criado): `Ativa, Baixada, Suspensa, Inapta, Nula, Desconhecida` (6 valores). `Nula` passa a ser um estado real e distinto (situação cadastral "NULA" da Receita Federal/BrasilAPI); `Desconhecida` é o estado seguro de fallback para texto externo não reconhecido — nunca lança exceção. `NaoEncontrada` foi removida do enum (estava sobrecarregada; não corresponde a nenhuma situação cadastral real da Receita).

**Regra para situação desconhecida:** `MapSituacao` em `BrasilApiCnpjProvider` cai em `SituacaoCadastralCnpj.Desconhecida` para qualquer texto não reconhecido (fonte alterou o vocabulário, campo ausente/nulo) — nunca lança exceção, nunca interrompe a consulta.

**Separação "consulta falhou" × "situação cadastral":** `ConsultaCnpjResultado.SituacaoCadastral` passou a ser `SituacaoCadastralCnpj?` (nullable). `CriarSucesso` sempre recebe um valor concreto (nunca nulo); `CriarFalha` passa `null` — nenhuma falha carrega mais um valor de situação cadastral "placeholder". Efeito colateral corrigido: `FornecedorEnriquecimentoComparer` (alerta de situação não-Ativa) e o registro de histórico de auditoria (`FornecedorCnpjConsultaHistorico.Resultado`, coluna de texto livre `NOT NULL`) foram ajustados para tratar `null` explicitamente (`"N/A"` no histórico de auditoria — texto livre, não o contrato canônico) sem reintroduzir ambiguidade no enum de domínio.

**Mapping BrasilAPI → canônico** (inalterado na escolha do campo-fonte, ampliado nos valores): continua usando exclusivamente `descricao_situacao_cadastral` (texto), nunca `situacao_cadastral` (código numérico) — decisão já correta preexistente, mantida. `ATIVA→Ativa, BAIXADA→Baixada, SUSPENSA→Suspensa, INAPTA→Inapta, NULA→Nula`, qualquer outro valor (incluindo ausente/nulo) `→Desconhecida`.

**Representação JSON final:** adicionado `JsonStringEnumConverter` global via `builder.Services.ConfigureHttpJsonOptions` em `Program.cs` — todo enum do contrato HTTP (não apenas `SituacaoCadastralCnpj`) agora serializa como o **nome do valor em string** (`"Ativa"`, `"Nula"`, `"Desconhecida"`, etc.), nunca como o inteiro subjacente. `SituacaoCadastral` serializa como `null` explícito em toda falha. Esta mudança também corrige silenciosamente o mesmo problema estrutural para `TipoErroConsultaCnpj`/`StatusConsultaCnpj` (B2.4), que dependiam da mesma configuração ausente sem que nenhum teste anterior tivesse exercitado a serialização HTTP real — testado explicitamente nesta WO (`ConsultaCnpjResultadoSerializationTests.cs`).

**Contrato TypeScript final** (`linxSupplierContract.ts`): `SituacaoCadastralCnpj = "Ativa" | "Baixada" | "Suspensa" | "Inapta" | "Nula" | "Desconhecida"` — union finito, sem `| string` residual, sem aceitar `number`. `ConsultaCnpjResultado.situacaoCadastral` passou a `SituacaoCadastralCnpj | null | undefined` (opcional), refletindo que só existe em sucesso.

**Alterações em `StatusBadge`/apresentação:** `StatusBadge.tsx` (componente genérico e compartilhado com toda a Administração — Filial, Centro de Custo, Perfil, Usuário, Unidade de Alocação, Unidade de Negócio, Identity Providers, Regras de Workflow/Orçamento — via `tone="situacao"`/`"decisao"` para Ativo/Inativo/Pendente/Aceito/Rejeitado) **não foi generalizado nem quebrado**: manter compatibilidade com esses ~15 call-sites não relacionados a CNPJ era um requisito explícito da Work Order. Em vez disso, foi criado um componente novo e dedicado, `SituacaoCadastralBadge.tsx` (`procurement/suppliers/components/`), usado exclusivamente por `SupplierComparison.tsx` para a situação cadastral do CNPJ. Ele usa um mapping explícito `Record<SituacaoCadastralCnpj, {label, className}>` — nunca deriva classe/label concatenando o valor recebido, nunca chama `.toLowerCase()`/`.toUpperCase()` sobre o valor, aceita `null`/`undefined`/qualquer valor não reconhecido em runtime e cai no estado neutro "Desconhecida" sem lançar exceção.

**Estratégia de labels/tone:** mapping estático (`Ativa→"Ativa"/status-ativa`, ..., `Desconhecida→"Desconhecida"/status-desconhecida`) — valor técnico e label de apresentação já coincidem em português correto para os 6 estados (não há transformação de caixa em runtime). Classes CSS `status-nula`/`status-desconhecida` adicionadas a `styles.css` (as duas únicas que não existiam antes).

**Confirmação de eliminação do crash `.toLowerCase()`:** para a situação cadastral do CNPJ, especificamente — sim, estruturalmente eliminado. `SituacaoCadastralBadge` nunca chama `.toLowerCase()`/`.toUpperCase()` sobre o valor recebido; testado explicitamente com um valor numérico injetado via `as unknown as SituacaoCadastralCnpj` (simulando o bug pré-B2.5) sem lançar exceção. O `StatusBadge` genérico (fora do escopo desta WO) continua usando `.toLowerCase()` para o tone `"situacao"` de Administração, mas nunca mais recebe situação cadastral de CNPJ — a rota que causava o crash real foi removida, e a causa raiz (ausência de `JsonStringEnumConverter`) foi corrigida na fonte.

**Testes backend adicionados (15 novos, `dotnet test`):** `BrasilApiCnpjProviderTests.cs` — mapeamento de cada situação conhecida (`Suspensa`, `Inapta`, `Nula`, incluindo texto em caixa baixa), texto não reconhecido → `Desconhecida`, campo ausente → `Desconhecida`, toda falha (`NaoEncontrado`) nunca carrega situação cadastral (`null`). `ConsultaCnpjResultadoSerializationTests.cs` (novo arquivo) — contrato HTTP real (com o mesmo `JsonStringEnumConverter` registrado em `Program.cs`): cada um dos 6 valores serializa como string explícita, `null` explícito em falha, `TipoErroConsultaCnpj`/`StatusConsultaCnpj` (B2.4) preservados como string.
