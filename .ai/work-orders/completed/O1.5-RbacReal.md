## Arquitetura implementada

Fluxo completo do ciclo RBAC, do dado ao enforcement:

```
Perfil ──(PerfisPermissoes)── Permissao          [catálogo global, seed determinístico]
  │
  └──(UsuariosPerfis)── Usuario
                          │
                          ▼
        PermissoesEfetivasResolver  (Infrastructure — consulta EF Core)
          união dos Perfis ATIVOS vinculados, deduplicada
                          │
                          ▼
        ObterIdentidadeAtualUseCase  (Application — revalida sessão + permissões por requisição)
                          │
                          ▼
        SessionCookieAuthenticationHandler  (Api — publica claims `maiscompras_permissao`)
                          │
                          ▼
        HttpContext.User → PermissaoAuthorizationHandler → policy `permissao:<Codigo>`
                          │
                          ▼
        Endpoint protegido: 401 (sem sessão) / 403 (sem permissão) / 200 (autorizado)
```

Camadas seguem o mesmo padrão físico de O1.4.2/O1.4.3 (`Domain/Identity`, `Application/Identity`, `Infrastructure/Identity`, `Api/Authorization`, `Api/Administration`). Frontend: Vertical Slice `administration/profiles` já existente, convertida para consumir a API real.

**Fonte central única:** `Domain/Identity/PermissaoCatalogo.cs` declara os 14 códigos de permissão com Ids estáveis. Policies, seed de banco, endpoints protegidos e o catálogo devolvido ao frontend derivam todos dele — nenhum código de permissão é escrito literalmente em outro lugar (elimina o antipadrão de "strings mágicas duplicadas" vedado pela Work Order).

## Banco

Migration `20260811143355_AddRbacPerfilPermissaoCatalogo` (gerada por `dotnet ef migrations add`, com dois blocos de SQL acrescentados manualmente e documentados no próprio arquivo):

- `Perfis`: novas colunas `Descricao` (nvarchar(400), NOT NULL, default `''`), `CriadoEm` e `AtualizadoEm` (datetimeoffset, NOT NULL).
- `Permissoes`: `Descricao` estreitada de nvarchar(max) para nvarchar(400); **seed das 14 permissões** do catálogo, com Ids estáveis.
- `PerfisPermissoes`: FKs para `Perfis` e `Permissoes`, `ON DELETE RESTRICT`, + índice em `PermissaoId`.
- `UsuariosPerfis`: FKs para `Usuarios` e `Perfis`, `ON DELETE RESTRICT`, + índice em `PerfilId`.
- SQL manual (1): backfill de `CriadoEm`/`AtualizadoEm` das linhas de Perfil pré-existentes (evita o `0001-01-01` que o EF usaria como default).
- SQL manual (2): **backfill idempotente** concedendo o catálogo completo aos Perfis `Administrador Sênior` já existentes. Sem ele, o único administrador do ambiente ficaria com 403 permanente e o RBAC nasceria irrecuperável pela própria aplicação.

Índice único `IX_Perfis_UnidadeNegocioId_Nome` (de O1.4.3.1) **reaproveitado**, não recriado.

Migration aplicada ao banco de desenvolvimento `MaisCompras` em 11/08/2026 (necessária para o smoke test real exigido pela seção 12 das instruções). `has-pending-model-changes`: limpo. `migrations script 0`: exatamente 1 `CREATE TABLE [Fornecedores]` histórico, inalterado.

## Segurança e autorização

Security Validation **independente** executada em 11/08/2026 por revisor logicamente isolado (sem acesso ao raciocínio do implementador), cobrindo 14 classes de ataque/falha contra o código real — mesmo padrão da O1.4.3.4/O1.4.3. Veredito **APROVADA COM RESSALVAS**; 1 HIGH + 2 MEDIUM + 1 LOW corrigidos nesta sprint com teste de regressão, ressalvas remanescentes registradas em `.ai/BACKLOG.md`. Detalhe completo em `.ai/CURRENT_SPRINT.md`.

Decisões de segurança materializadas em código:

- Unidade de Negócio sempre da identidade autenticada, nunca do payload — isolamento entre BUs comprovado por teste.
- Códigos de permissão fora do catálogo são rejeitados (400), nunca ignorados.
- Claims de permissão emitidas exclusivamente pelo servidor; header forjado pelo cliente é ignorado (teste dedicado).
- Permissões reresolvidas a cada requisição — revogação tem efeito imediato, sem esperar expiração de sessão.
- Invariante anti-auto-bloqueio: nenhuma operação pode deixar a Unidade de Negócio sem Perfil ativo com `Perfil.Gerenciar` (409).
- Perfil inativo não contribui nenhuma permissão efetiva.
- Nenhuma tabela de permissão por usuário existe no modelo — teste de modelo falha se alguém introduzir uma.
- **Não-escalonamento de privilégio:** ninguém concede permissão que não possui (403). Fecha o achado HIGH da validação independente.
- **Invariante anti-auto-bloqueio exige usuário vinculado:** um Perfil administrativo sem ninguém vinculado não conta como salvaguarda.
- **Permissões efetivas escopadas à Unidade de Negócio da sessão**, impedindo escalonamento entre tenants.
- **CSRF no nível do grupo**, ciente de métodos seguros: endpoint novo nasce protegido.
