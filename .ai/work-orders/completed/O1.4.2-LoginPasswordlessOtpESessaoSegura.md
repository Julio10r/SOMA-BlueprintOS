# Work Order O1.4.2 — Login Passwordless OTP e Sessão Segura

Status:
✅ Concluída (07/08/2026), incluindo as micro-iterações O1.4.2.1 e O1.4.2.2 — Work Order aberta retroativamente em 10/08/2026, durante a auditoria de consolidação Git posterior ao fechamento da O1.4.3, para regularizar a rastreabilidade documental (entrega catalogada como "Concluída" em `.ai/BACKLOG.md` e `.ai/PROJECT_STATE.md`, mas sem arquivo próprio em `.ai/work-orders/completed/`).

## Observação sobre a natureza retroativa

Esta Work Order documenta uma implementação já concluída e em uso (Vertical Slice de autenticação, backend + frontend), com histórico completo de três Security Validations independentes já registrado em `.ai/CURRENT_SPRINT.md`. Nenhuma evidência foi criada retroativamente.

## Objetivo

Implementar o primeiro fluxo real de autenticação Passwordless do +Compras em Development: solicitação de OTP, geração segura do desafio, validação, criação de sessão server-side, cookie seguro, identidade autenticada, logout. Sem Entra ID, sem provider corporativo de e-mail real, sem Bootstrap completo (preparado, não implementado nesta Work Order).

## Decisões de produto ratificadas na abertura (07/08/2026)

- Permissões: catálogo global (`PEDIDO.CRIAR`, `USUARIO.GERENCIAR`, etc.), sem permissão individual por usuário.
- Perfis configurados por Unidade de Negócio; usuário pode ter 1..N Perfis; permissões efetivas = união dos Perfis.
- Administrador Sênior: Perfil especial de plataforma, modelo preparado nesta sprint (Bootstrap completo não implementado agora).
- Usuário × Centro de Custo: vínculo 1..N, conceito de escopo operacional distinto de Perfil.
- Modelo de sessão ratificado: sessão persistida server-side, identificador opaco em cookie `HttpOnly/Secure/SameSite=Strict`, sem JWT stateless, sem dados de identidade/autorização no cookie.

## Entregas

**Backend** (`Domain/Identity`, `Application/Identity`, `Infrastructure/Identity`, `Api/Auth` + `Api/Identity`): entidades `UnidadeNegocio`, `Usuario`, `Perfil`, `Permissao`, `PerfilPermissao`, `UsuarioPerfil`, `UsuarioCentroCusto`, `CodigoVerificacaoOtp`, `SessaoAutenticacao`; casos de uso `SolicitarOtpUseCase`, `ValidarOtpUseCase`, `LogoutUseCase`, `ObterIdentidadeAtualUseCase`; contrato `IOtpEmailSender`; `DevelopmentOtpEmailSender` + `UnconfiguredCorporateOtpEmailSender` (fail-closed); endpoints `POST /auth/otp/request`, `POST /auth/otp/verify`, `POST /auth/logout`, `GET /auth/me`; `GET /dev/otp` (exclusivo de Development, loopback); `SessionCurrentIdentity`; rate limiting por IP; CSRF por header customizado; headers de segurança; CORS com allowlist; migration `AddIdentityAuthentication`.

**Frontend** (`auth/`): `LoginPage`, `AuthContext`/`AuthProvider`/`useAuth`, `RequireAuth`, integração em `AppRoutes.tsx`/`AppShell.tsx`. Nenhum dado de sessão/OTP em `localStorage`/`sessionStorage`.

**O1.4.2.1 — Security Hardening (07/08/2026):** fechamento dos achados ALTO A–D e MÉDIO/N da 1ª Security Validation independente — throttle server-side por e-mail (`OtpRequestThrottle`), atomicidade de OTP via RowVersion + índice único filtrado, `AuthorizationOptions.FallbackPolicy` secure-by-default, hardening de `/dev/otp`, fail-closed comprovado por host real. Migration `AddOtpHardening`.

**O1.4.2.2 — Hardening do `DevelopmentHeaderAuthenticationHandler` (07/08/2026):** fechamento do achado ALTO E da 2ª Security Validation independente — exigência de origem estritamente loopback no handler.

## Resultado

**Security Implementation Gate III: APROVADO COM PENDÊNCIAS NÃO BLOQUEANTES PARA DEVELOPMENT.** Com este Gate, a O1.4.2 satisfez integralmente a exigência de ADR-0020 (item 13). Pendências carregadas para o Authentication Infra Readiness Gate, a resolver antes de Homologação: validação de RowVersion+índice único filtrado em provider relacional real; CSP efetiva da SPA; `EmailAuditHasher` sem salt/HMAC; sincronização de migrations do banco compartilhado; provedor corporativo/Entra ID postergados.
