**Status:** ✅ CONCLUÍDA (10/08/2026). As 4 etapas técnicas — O1.4.3.1 (Fundação Backend), O1.4.3.2 (Conclusão Transacional e Administrador Sênior), O1.4.3.3 (Frontend Bootstrap) e O1.4.3.4 (Security Self-Review dedicada + preparação da Security Validation independente) — estão todas ✅ CONCLUÍDAS (ver seção 21). A **Security Validation independente** foi executada por um revisor isolado (sem acesso prévio aos achados da Self-Review), cobrindo as 13 áreas obrigatórias de escopo (takeover, Bootstrap Secret, allowlist, OTP, BootstrapSession, CSRF, rate limiting, atomicidade, concorrência, invariante do Administrador Sênior, autorização, superfícies de Development, pós-Bootstrap): **0 CRITICAL, 0 HIGH**. Parecer: **APROVADA COM RESSALVAS**. As duas divergências identificadas entre a Self-Review e a Security Validation independente (loopback de `DevelopmentRequestIdentity`; detecção de índice único por mensagem) foram reconciliadas por leitura direta do código — nenhuma subiu de severidade; ambas desceram (INFORMATIONAL e MEDIUM→LOW). **O Product Owner aceitou formalmente as ressalvas em 10/08/2026.** A O1.4.3, como um todo, está **FORMALMENTE CONCLUÍDA** e esta Work Order foi movida para `.ai/work-orders/completed/`. Os findings remanescentes (4 MEDIUM, 6 LOW, 5 INFORMATIONAL) foram registrados no backlog técnico (`.ai/BACKLOG.md`) — nenhum é bloqueante para esta Work Order; dois (Cache-Control `no-store` em `/bootstrap/*`; entropia do Bootstrap Secret) **bloqueiam explicitamente a promoção para Homologação** até serem tratados e revalidados. ## 1. Objetivo

Transformar o Security Design Review aprovado (`docs/architecture/security-design-auth-o1.4.md`, seção 20 — **Bootstrap Security Design Gate: APROVADO COM PENDÊNCIAS**, nenhuma bloqueante) em um plano técnico executável: fluxo completo, responsabilidades por camada, contratos de API, modelo de dados, estratégia de testes e critérios de aceite para implementar o Bootstrap Mode e o perfil "Administrador Sênior" do +Compras (ADR-0020, item 12).

## 2. Contexto

A O1.4.2 (Login Passwordless OTP e Sessão Segura), incluindo as micro-iterações O1.4.2.1 (Security Hardening) e O1.4.2.2 (Hardening do `DevelopmentHeaderAuthenticationHandler`), está formalmente concluída — **Security Implementation Gate III: APROVADO COM PENDÊNCIAS NÃO BLOQUEANTES PARA DEVELOPMENT** (`.ai/CURRENT_SPRINT.md`, `.ai/PROJECT_STATE.md`). A O1.4.3 (Security Design Review do Bootstrap) também está concluída, com Gate aprovado com pendências não bloqueantes (`docs/architecture/security-design-auth-o1.4.md`, §20.22). Esta Work Order é o passo seguinte: detalhamento técnico, ainda sem implementação.

## 3. Decisões já ratificadas pelo Product Owner (tratar como definitivas, não redecidir)

1. Bootstrap utiliza sessão própria, distinta da sessão normal, com privilégios estritamente limitados.
2. Após a conclusão do Bootstrap, o sistema nunca poderá ficar sem pelo menos um Administrador Sênior ativo.
3. Pode existir mais de um Administrador Sênior.
4. Bootstrap nunca reabre automaticamente.
5. Inativação/remoção do último Administrador Sênior ativo deve ser bloqueada.
6. Recovery pós-Bootstrap é procedimento separado e não reabre o Bootstrap.
7. Bootstrap exige conjuntamente Bootstrap Secret + identidade pré-autorizada + OTP válido — nenhum fator isoladamente autentica.
8. Conclusão deve ser transacional e permitir somente uma conclusão válida.

## 4. Divergências encontradas entre o Security Design, os documentos de produto e o código real

Leitura integral de ADR-0020, `security-design-auth-o1.4.md`, `domain-principles.md`, `ENGINEERING_BLUEPRINT.md`, `PROJECT_STATE.md`, `CURRENT_SPRINT.md`, `BACKLOG.md`, `ComprasFuncional.md`, `ComprasUX.md`, `ComprasDataModel.md`, e do código real de `Domain/Identity`, `Application/Identity`, `Infrastructure/Identity`, `Api/Auth`, `Api/Identity`, `Api/Middleware`, `frontend/web/src/auth` e `frontend/web/src/core` confirmou as seguintes divergências, nenhuma delas bloqueante, todas a resolver nesta Work Order:

1. **Fluxo funcional do wizard não reflete os três fatores de autenticação exigidos pelo Security Design.** `ComprasFuncional.md`/`ComprasUX.md` (seção "Bootstrap") descrevem um wizard de 3 passos visíveis — (1) Unidade de Negócio, (2) Administrador Sênior, (3) confirmação — sem menção a Bootstrap Secret ou OTP. Este é um artefato do momento em que essas telas foram especificadas (R1.2, antes da revisão de segurança de O1.4.3). **Resolução adotada nesta Work Order (seção 7):** um "passo 0" de portão de segurança (secret + e-mail pré-autorizado → OTP) precede o wizard de 3 passos já especificado — o wizard funcional permanece válido para a parte de coleta de dados de negócio (BU + Administrador), mas só é alcançável depois do portão de segurança. `ComprasFuncional.md`/`ComprasUX.md` devem ser atualizados para refletir esse passo 0 explicitamente (fora do escopo desta Work Order — recomendação registrada na seção "Pendências").
2. **CQRS/MediatR (ADR-0001/ADR-0003) não é usado pela Vertical Slice de Identity.** `AuthController` injeta diretamente `ISolicitarOtpUseCase`/`IValidarOtpUseCase`/`ILogoutUseCase`/`IObterIdentidadeAtualUseCase` — não há `IMediator.Send(...)`/`IRequestHandler<T>`. Isso já é o padrão estabelecido por toda a O1.4.2 (não introduzido por esta Work Order); Bootstrap deve seguir o **mesmo padrão de casos de uso diretos**, por consistência com o código já existente, não o padrão MediatR de outros módulos mais antigos (Fornecedores). Divergência pré-existente, não desta etapa — registrada para rastreabilidade, sem ação corretiva aqui.
3. **`SessaoAutenticacao` não possui `IdentityProviderId`**, embora `ComprasDataModel.md` (linha 679, entidade `SessaoAutenticacao`) o descreva como campo esperado. Não bloqueia Bootstrap (a sessão Bootstrap é uma entidade nova e distinta, seção 7) — registrado como divergência pré-existente da O1.4.2, fora do escopo de correção desta Work Order.
4. **`Perfil` não tem índice único por (`UnidadeNegocioId`, `Nome`)**, apesar de `ComprasDataModel.md` indicar essa necessidade ("Índice único em nome do perfil, por Unidade de Negócio"). Relevante para Bootstrap porque a etapa de conclusão faz "criar ou reaproveitar" o Perfil "Administrador Sênior" (seção 9) — sem esse índice, uma corrida teórica poderia criar dois Perfis com o mesmo nome na mesma BU. **Ação desta Work Order:** adicionar esse índice único na migration da O1.4.3 (seção 12), fechando a divergência como parte da própria entrega, não apenas registrando-a.
5. **Nenhuma migration aplicada no banco compartilhado `MaisComprasConnection`** desde a dessincronia já registrada em O1.4.2 (`Invalid object name 'Usuarios'`/`already an object named 'Fornecedores'`). Migrations desta Work Order (seção 12) devem ser projetadas, mas **não aplicadas** nesse banco — ver seção "Migrations" e "Proibições Operacionais".
6. Nenhuma outra divergência material encontrada entre o Security Design (seção 20 de `security-design-auth-o1.4.md`) e o código real de O1.4.2/O1.4.2.1/O1.4.2.2 — os padrões de OTP hash/salt/RowVersion, `AuthorizationOptions.FallbackPolicy`, seleção por `IHostEnvironment`, `CsrfHeaderFilter`, `RateLimitingPolicies` e `SecurityHeadersMiddleware` já implementados são exatamente os que o Security Design do Bootstrap (seção 20 de `security-design-auth-o1.4.md`) assume como reaproveitáveis.

## 7. Arquitetura técnica proposta e fluxo completo

```
Bootstrap disponível (BootstrapEstado.Concluido == false)
  │
  ▼
GET /bootstrap/estado (anônimo) ── frontend decide /login vs. /bootstrap
  │
  ▼
[Passo 0 — portão de segurança, não visível como "passo" no wizard de produto]
POST /bootstrap/iniciar { email, secret }  (anônimo; rate limit próprio)
  │  valida, nesta ordem: Concluido==false → secret (tempo constante) → email na allowlist
  │  → reaproveita SolicitarOtpUseCase (contexto Bootstrap) → CodigoVerificacaoOtp emitido
  ▼
POST /bootstrap/otp/verificar { email, codigo }  (anônimo; rate limit próprio)
  │  reaproveita ValidarOtpUseCase (contexto Bootstrap)
  │  sucesso → cria BootstrapSessao (nova entidade, seção 8) → cookie BootstrapSession próprio
  ▼
[Passo 1 — wizard de produto, ComprasFuncional.md/ComprasUX.md, agora sob BootstrapSession válida]
POST /bootstrap/unidade-negocio { nome, slug }  (BootstrapAuthenticated)
  │  cria UnidadeNegocio (ou reaproveita uma existente sem Administrador Sênior — seção 20.3
  │  de security-design-auth-o1.4.md) — NÃO persiste ainda; mantida no estado da BootstrapSessao
  │  até a conclusão (ver nota de atomicidade abaixo) OU persiste isoladamente e é revertida via
  │  compensação se a conclusão falhar (decisão de implementação, seção 9)
  ▼
[Passo 2 — dados do Administrador Sênior, mesmo wizard]
(coletado no mesmo payload de /bootstrap/concluir, não em endpoint próprio — ver seção 13)
  ▼
[Passo 3 — confirmação explícita, ComprasUX.md]
POST /bootstrap/concluir { unidadeNegocio, administrador }  (BootstrapAuthenticated)
  │  TRANSAÇÃO ÚNICA (seção 9): cria/confirma UnidadeNegocio + cria Usuario + garante Perfil
  │  "Administrador Sênior" + cria UsuarioPerfil + UPDATE condicional BootstrapEstado.Concluido
  │  (WHERE Concluido = 0) + auditoria
  ▼
Bootstrap Concluido=true → BootstrapSessao invalidada (uso único) → resposta de sucesso
  ▼
Frontend redireciona para /login (fluxo normal de autenticação regular, O1.4.2)
```

**Nota de atomicidade (decisão de implementação a fixar na Etapa 2, seção 11):** para não introduzir uma segunda transação de longa duração através de múltiplas requisições HTTP (passo 1 → passo 3), o payload completo de Unidade de Negócio e Administrador Sênior é coletado no frontend ao longo do wizard mas **enviado em uma única chamada** a `POST /bootstrap/concluir` — o "passo 1" acima não é obrigatoriamente um endpoint HTTP próprio; pode ser validação client-side apenas, com persistência real ocorrendo inteiramente dentro da transação de `/bootstrap/concluir`. Esta é a opção recomendada (evita estado parcial em múltiplas requisições); a alternativa de um endpoint intermediário que persiste a BU antes da confirmação final é tecnicamente viável mas exige uma estratégia de compensação (rollback manual se o passo 3 falhar) que este design considera desnecessariamente complexa para o ganho de UX que traria.

## 8. Sessão Bootstrap — projeto técnico

Reaproveita a mesma primitiva criptográfica de sessão já usada em O1.4.2 (`OpaqueSessionToken` — identificador opaco ≥256 bits/CSPRNG, hash SHA-256 armazenado no servidor, valor bruto nunca persistido), aplicada a uma entidade e cookie **próprios**, nunca a `SessaoAutenticacao`/`AuthCookie` existentes.

- **Entidade:** `BootstrapSessao` (`Domain/Identity`), campos: `Id`, `EmailCandidato` (já validado por OTP), `IdentificadorHash`, `CreatedAt`, `ExpiresAt` (curta duração, recomendado 15 minutos — alinhado à validade de OTP), `UsadaEm` (nullable — marca uso único no sucesso), `RevokedAt` (nullable — para invalidação explícita em falha definitiva). **Sem `UsuarioId`** — o usuário ainda não existe até a conclusão.
- **Token/hashing:** idêntico a `OpaqueSessionToken.GenerateRawToken()`/`.Hash()` — reaproveitado diretamente, sem duplicar a primitiva criptográfica.
- **Duração:** 15 minutos, absoluta — sem renovação por atividade (ao contrário da sessão normal, seção 3.2, que tem expiração por inatividade); um fluxo de Bootstrap não deve poder ficar "pendurado" indefinidamente por atividade intermitente.
- **Revogação:** `RevokedAt` setado em qualquer falha definitiva (ex.: `/bootstrap/concluir` retorna erro de negócio, não apenas erro transitório) e sempre após uso bem-sucedido (`UsadaEm`) — a sessão Bootstrap nunca é reutilizável, mesmo dentro do prazo de expiração.
- **Cookie:** nome próprio, ex. `mc_bootstrap_sid` (nunca `AuthCookie.Name`), mesmas flags de segurança (`HttpOnly`, `Secure`, `SameSite=Strict`).
- **Claims/escopo:** o `AuthenticationHandler` de Bootstrap publica em `HttpContext.User` apenas uma claim de "sessão Bootstrap válida" + o e-mail candidato (para exibição em UX, "identidade que está executando esta etapa") — nunca uma claim de papel/perfil, nunca `ClaimTypes.Role`.
- **Persistência:** tabela própria (`BootstrapSessoes`), com o mesmo padrão de índice em `IdentificadorHash` já usado para `SessaoAutenticacao` (índice único, `HasIndex(x => x.IdentificadorHash).IsUnique()`).
- **Relacionamento com identidade/e-mail:** 1:1 com o e-mail candidato validado por OTP para aquela tentativa específica; uma nova tentativa (`POST /bootstrap/iniciar`) sempre invalida qualquer `BootstrapSessao` anterior do mesmo e-mail ainda não usada (mesmo princípio de invalidação em cascata já usado para OTP, `InvalidarPorNovoCodigo`).
- **Comportamento após Bootstrap concluído:** nenhuma `BootstrapSessao` sobrevive de forma útil — a política de autorização `BootstrapAuthenticated` (seção 8.1) sempre checa `BootstrapEstado.Concluido == false` **além** da validade da sessão; mesmo que uma `BootstrapSessao` não expirada exista tecnicamente (ex.: criada segundos antes de outra tentativa concorrente vencer a corrida de conclusão), ela para de autorizar qualquer coisa no instante em que `Concluido = true`.

### 8.1 Autorização — `BootstrapSession` vs. sessão normal

Dois `AuthenticationScheme`s adicionais aos já existentes (`SessionCookie`, `DevelopmentHeader`) — **não modificam nenhum dos dois existentes**:

- **`BootstrapSessionAuthenticationHandler`** (novo, todos os ambientes — Bootstrap não é exclusivo de Development, seção 15): lê o cookie próprio, resolve `BootstrapSessao` válida e não usada, publica a claim de sessão Bootstrap.
- **Política de autorização `BootstrapAuthenticated`** (nova, via `AuthorizationPolicyBuilder`, registrada em `AddAuthorization` ao lado da `FallbackPolicy` já existente — **a `FallbackPolicy` global não é alterada**): exige o esquema `BootstrapSession` autenticado **e** `BootstrapEstado.Concluido == false` (checagem adicional, não apenas presença de claim — via `IAuthorizationRequirement` customizado ou verificação direta no handler do endpoint).
- Os dois endpoints de mutação de negócio (`/bootstrap/concluir`, e o endpoint intermediário se a Etapa de implementação decidir por um) usam `[Authorize(Policy = "BootstrapAuthenticated")]` — nunca a `FallbackPolicy` padrão (que exigiria sessão normal, inexistente neste fluxo) e nunca `AllowAnonymous()`.

**Tabela de exceções — nenhum `if` espalhado em controllers, apenas atributos/`RequireAuthorization` explícitos por rota:**

| Endpoint | Classificação | Justificativa |
|---|---|---|
| `GET /bootstrap/estado` | `AllowAnonymous` | Leitura pública mínima (disponível/concluído), necessária antes de qualquer sessão existir. |
| `POST /bootstrap/iniciar` | `AllowAnonymous` | Entrada do fluxo — protegido por secret + allowlist + rate limiting, não por sessão prévia. |
| `POST /bootstrap/otp/verificar` | `AllowAnonymous` | Idem — mas só produz efeito para uma tentativa já iniciada. |
| `POST /bootstrap/concluir` | `BootstrapAuthenticated` | Operação de maior privilégio do fluxo — exige `BootstrapSessao` válida. |
| Qualquer endpoint de negócio existente (Fornecedores, Auth normal, etc.) | inalterado | Continuam sob `FallbackPolicy`/`SessionCookie`/`DevelopmentHeader` — Bootstrap nunca intercepta ou reusa esses esquemas. |

Nenhuma flag booleana arbitrária ("modoBootstrap = true" em algum estado global) e nenhuma confiança no frontend para impedir acesso — toda a decisão de autorização vive no `AuthenticationHandler`/`AuthorizationPolicy` do backend.

## 9. Bootstrap Secret — implementação concreta

- **Options:** `BootstrapSecretOptions` (`Application/Identity/Models` ou `Bootstrap/Models`, decisão de namespace na implementação), com propriedade `Secret` (string). Seção de configuração: `Bootstrap:Secret`.
- **Validação de startup:** `services.AddOptions<BootstrapSecretOptions>().Bind(...).ValidateOnStart()` com um `IValidateOptions<BootstrapSecretOptions>` customizado que falha se `Secret` estiver vazio/nulo **enquanto `BootstrapEstado.Concluido == false`** — mesmo padrão de `CorporateOtpEmailSenderOptionsValidator` já usado para o provider corporativo de e-mail. **Refinamento necessário:** a validação de startup não tem acesso trivial ao banco (`Concluido`) no momento do boot — recomenda-se validar apenas presença do secret sempre que o ambiente não for Development (fail-closed incondicional, mais simples e mais seguro do que tentar consultar o banco durante `ValidateOnStart()`), aceitando que, em ambientes onde o Bootstrap já foi concluído há muito tempo, o secret configurado continua tecnicamente exigido no startup mas nunca é lido em runtime (inócuo, seção 20.10 do Security Design).
- **Fail-closed:** ausência do secret fora de Development impede a aplicação de subir (mesmo mecanismo de `ValidateOnStart()`); em Development, o secret é opcional apenas se `Concluido == true` no ambiente local — se `Concluido == false` e o secret estiver ausente em Development, o endpoint de início deve responder erro de configuração explícito (nunca aceitar um secret vazio como "sempre válido").
- **Comparação em tempo constante:** `CryptographicOperations.FixedTimeEquals` sobre os bytes UTF-8 do valor recebido vs. configurado — nunca `string.Equals`/`==`.
- **Comportamento se ausente:** endpoint `/bootstrap/iniciar` responde a mesma resposta genérica de rejeição usada para secret incorreto (nunca revela "secret não configurado" como categoria de erro distinta ao cliente).
- **Comportamento após Bootstrap concluído:** irrelevante — `/bootstrap/iniciar` já responde 404 antes de qualquer comparação de secret (seção 20.10 do Security Design, reafirmada aqui).
- **Não armazenar no banco:** confirmado — vive exclusivamente em User Secrets (Development) / secret manager corporativo (Homologação/Produção), nunca em `BootstrapEstado` ou qualquer outra tabela.
- **Não hashear sem razão:** confirmado — como o secret nunca é persistido pela aplicação (só comparado em memória contra o valor de configuração), não há necessidade de hash; hashear traria custo de manutenção sem benefício de segurança adicional, já que o único lugar onde o valor "em claro" existe é a configuração, que já é protegida pelo secret manager.

## 10. Allowlist de identidades autorizadas — implementação concreta

- **Options:** `BootstrapAllowedCandidatesOptions`, propriedade `Emails` (`string[]`). Seção de configuração: `Bootstrap:AllowedCandidateEmails`.
- **Normalização:** mesma função já usada para `OtpRequestThrottle`/`Usuario.Email` (trim + `ToLowerInvariant()`) — aplicada tanto à configuração (na leitura) quanto ao e-mail recebido na requisição, antes de qualquer comparação.
- **Validação:** nenhuma validação de formato de e-mail além da já existente no fluxo de OTP normal (reaproveitar, não duplicar).
- **Armazenamento:** array de strings em configuração — User Secrets (Development) / secret manager corporativo (Homologação/Produção). **Nunca no repositório** — `appsettings.json` versionado não deve conter e-mails reais; se um exemplo for necessário em `appsettings.json`, usar um placeholder claramente fictício (ex.: `"admin.inicial@example.invalid"`), nunca um endereço real de pessoa.
- **Fail-closed:** se a lista estiver ausente/vazia e `Concluido == false`, o Bootstrap fica **efetivamente indisponível** (nenhum e-mail passa a checagem de allowlist) — não é um erro de startup (a aplicação sobe normalmente), mas uma configuração operacional pendente. Recomenda-se um log de nível `Warning` no startup, fora de Development, alertando que o Bootstrap está configurado sem candidatos — nunca um bypass "lista vazia = qualquer um passa".
- **Comportamento para lista vazia:** tratado explicitamente acima — nunca interpretado como "sem restrição".

## 11. Reutilização de OTP — o que é reaproveitado e o que precisa de adaptação

**Reaproveitado sem alteração:** `CodigoVerificacaoOtp` (entidade, hash/salt/RowVersion/uso único/tentativas), `OtpHasher`, `OtpCodeGenerator`, `OtpRequestThrottle` (throttle por e-mail), `IOtpEmailSender`/`DevelopmentOtpEmailSender`/`UnconfiguredCorporateOtpEmailSender` (fail-closed fora de Development).

**Adaptação necessária — distinguir OTP de login normal vs. OTP de Bootstrap:** `SolicitarOtpUseCase`/`ValidarOtpUseCase` atuais operam sobre um `Usuario` já existente (resolvido por e-mail antes de emitir o OTP). No fluxo de Bootstrap, o e-mail candidato **não corresponde a nenhum `Usuario` existente** (é precisamente o cenário de "ainda não existe ninguém"). Duas opções de implementação, avaliadas na Etapa 2:

- **Opção recomendada:** estender `CodigoVerificacaoOtp` para aceitar um `UsuarioId` nulo/opcional junto com o e-mail candidato diretamente (hoje a entidade já é construída a partir de `UsuarioId` — avaliar se o construtor precisa de uma sobrecarga ou se um `UsuarioId` sintético/reservado é aceitável). Reaproveita 100% do hashing/tentativas/expiração/RowVersion sem duplicar a classe.
- **Opção alternativa (não recomendada, mas viável):** uma entidade paralela `CodigoVerificacaoOtpBootstrap` — rejeitada por duplicar o mecanismo criptográfico (violando a instrução explícita de não duplicar), mesmo que a duplicação seja "só" de schema.

A decisão exata (ajuste de `CodigoVerificacaoOtp` vs. campo nulo vs. outra estratégia) é uma decisão de implementação da Etapa 1 (seção 16) — este documento fixa apenas a régua: **reaproveitar a mesma classe/mecanismo, nunca duplicar o hashing/tentativas/expiração.**

## 12. `BootstrapEstado` — hardening técnico

- **Entidade atual:** já modelada conceitualmente em `ComprasDataModel.md` (`Concluido`, `ConcluidoEm`, `UsuarioAdministradorSeniorId`) — **ainda não existe como classe em `Domain/Identity`** (divergência esperada, é o objeto desta Work Order, não uma falha de O1.4.2).
- **Configuração EF — garantia de linha única:** aplicar chave primária fixa (ex.: `Id` sempre igual a um GUID constante conhecido em código, nunca gerado) **ou** uma coluna computada/check constraint que force exatamente uma linha (ex.: coluna `Singleton` sempre `1`, com índice único). Recomenda-se a chave fixa — mais simples de implementar e de raciocinar (`INSERT`/`UPDATE` sempre referenciam o mesmo `Id` conhecido, nunca uma consulta "existe alguma linha?").
- **Inicialização:** seed migration que insere a linha única com `Concluido = false` na criação da tabela — elimina a ambiguidade "linha ausente = disponível" descrita no Security Design (seção 20.3) como aceitável, mas que é mais simples de garantir via seed do que via lógica de aplicação "trate ausência como false".
- **Concorrência:** `UPDATE BootstrapEstado SET Concluido = 1, ConcluidoEm = @agora, UsuarioAdministradorSeniorId = @id WHERE Id = @idFixo AND Concluido = 0` — o predicado `Concluido = 0` é o compare-and-swap; verificar `rowsAffected == 1` após o `SaveChangesAsync`/`ExecuteSqlRawAsync` (decisão de EF Core puro vs. SQL direto na Etapa 2). RowVersion como reforço adicional é aceitável, mas não estritamente necessário dado que a chave fixa já elimina ambiguidade de qual linha atualizar.
- **Integridade — linha ausente:** tratado pela seed migration (nunca deveria ocorrer em ambiente corretamente inicializado); se ocorrer por alguma falha operacional, o comportamento correto é **fail-closed**: `GET /bootstrap/estado` e `POST /bootstrap/iniciar` devem tratar "nenhuma linha encontrada" como **indisponível** (nunca como "disponível por omissão" em runtime, mesmo que a seção 20.3 do Security Design trate isso como equivalente a `false` — em runtime, na ausência da seed, o comportamento mais seguro é negar e logar erro, não assumir disponibilidade), permitindo que a operação seja corrigida por Infra antes de reabrir o Bootstrap.
- **Múltiplas linhas por corrupção:** com chave primária fixa, isso é estruturalmente impossível via EF Core (uma segunda linha exigiria burlar a PK, cenário de acesso direto ao banco fora do modelo de ameaça de aplicação, seção 20.12) — nenhuma lógica de aplicação extra necessária além de, defensivamente, sempre consultar por `Id = idFixo` explicitamente, nunca `SingleOrDefaultAsync()` sem filtro (que lançaria exceção se houvesse mais de uma linha, o que já é um fail-closed aceitável nesse cenário de corrupção).
- **Migration adicional:** índice único em `Perfil` por (`UnidadeNegocioId`, `Nome`) — fecha a divergência nº 4 da seção 4, necessária porque a conclusão do Bootstrap faz "criar ou reaproveitar" o Perfil "Administrador Sênior" (seção 9 da tarefa/seção 20.9 do Security Design).

## 13. Conclusão transacional — projeto da transação

`ConcluirBootstrapUseCase`, dentro de uma única transação de banco (`IDbContextTransaction` ou a transação implícita de um único `SaveChangesAsync()` com todas as operações no mesmo `DbContext`, que é o padrão mais simples e já suficiente aqui):

1. Ler `BootstrapEstado` (linha fixa) — se `Concluido == true`, abortar imediatamente com erro de negócio (não deveria ocorrer, dado que a `BootstrapAuthenticated` policy já checou isso, mas é a última barreira antes da escrita).
2. Criar ou reaproveitar `UnidadeNegocio` — se o payload referenciar uma BU existente sem Administrador Sênior, reaproveitar; caso contrário, criar nova (regra de negócio já fixada no Security Design, seção 20.3).
3. Criar `Usuario` (e-mail = o mesmo já validado por OTP na `BootstrapSessao` — **nunca aceitar um e-mail diferente no payload de conclusão do que o validado no passo 0**, para impedir que uma sessão Bootstrap válida seja usada para promover um e-mail diferente do que provou posse via OTP).
4. Garantir a existência do Perfil "Administrador Sênior" na BU escolhida — `SingleOrDefaultAsync` pelo índice único (`UnidadeNegocioId`, `Nome`) da seção 12; criar se ausente.
5. Criar `UsuarioPerfil` (vínculo).
6. Verificar `GarantirAdministradorSeniorAtivoRestante` (seção 10) — trivialmente satisfeita aqui (é a primeira criação), mas invocar o mesmo método de domínio por consistência de código, não uma cópia da regra.
7. `UPDATE` condicional de `BootstrapEstado` (seção 12) — se `rowsAffected == 0`, abortar toda a transação (outra conclusão venceu a corrida) e propagar um erro de negócio específico (`BootstrapJaConcluidoException` ou equivalente).
8. Registrar evento de auditoria "Bootstrap concluído" (seção 17 da tarefa/seção 20.19 do Security Design).
9. `SaveChangesAsync()` — se qualquer etapa acima lançar (incluindo violação do índice único de `Perfil` sob corrida, ou falha de concorrência), a transação inteira reverte; nenhum `Usuario`/`UnidadeNegocio`/`UsuarioPerfil` órfão persiste.
10. Sucesso → invalidar (`UsadaEm`) a `BootstrapSessao` usada.

**Estratégia de concorrência escolhida:** `UPDATE` condicional (compare-and-swap) sobre a linha fixa de `BootstrapEstado`, dentro da mesma transação/`SaveChangesAsync()` das demais escritas — não uma transação SQL explícita com `SERIALIZABLE` (mais pesada, não necessária dado que o CAS já resolve a corrida no nível certo) e não RowVersion isolado em `BootstrapEstado` (redundante com a chave fixa + predicado condicional, que já é suficiente). RowVersion permanece a estratégia correta para `CodigoVerificacaoOtp`/`OtpRequestThrottle` (já implementado, reaproveitado sem alteração) — não é reintroduzido aqui porque o padrão de linha única resolve o mesmo problema de forma mais simples.

## 14. Regra do último Administrador Sênior — onde ela deve viver

**Decisão: método de domínio reutilizável, não uma checagem duplicada em cada fluxo que possa violá-la.** Nome sugerido: `AdministradorSeniorInvariantService` (ou método estático em um agregado apropriado — decisão de implementação), com uma operação central: `GarantirQueRestaAoMenosUmAdministradorSeniorAtivo(unidadeNegocioId, exceto: usuarioIdOuVinculoSendoRemovido)`, chamada **antes** de persistir qualquer uma das seguintes operações (identificadas nesta revisão como os fluxos futuros que podem violar a invariante — nenhum deles implementado ainda, portanto nenhuma ação de código aqui, apenas identificação para a Work Order que os implementar):

- Inativar `Usuario` que possua o Perfil "Administrador Sênior" ativo.
- Remover o vínculo `UsuarioPerfil` de um usuário com o Perfil "Administrador Sênior".
- Inativar o próprio Perfil "Administrador Sênior" (removeria as permissões efetivas de todos os vinculados a ele simultaneamente).
- Qualquer futura funcionalidade de "excluir usuário" (hoje não existe exclusão física de usuário no sistema, ver `ComprasDataModel.md`/módulos de Administração — mas se vier a existir, deve respeitar a mesma invariante).
- Alteração de Unidade de Negócio de um usuário Administrador Sênior, se um dia essa operação existir (hoje `Usuario.UnidadeNegocioId` é definido na criação e não há fluxo de "mover usuário de BU").

**Nesta Work Order:** apenas identificar o método/local e chamá-lo trivialmente no fluxo de conclusão do Bootstrap (onde a invariante é satisfeita por construção, passo 6 da seção 13). **Não implementar** os bloqueios nos fluxos futuros de inativação/remoção listados acima — isso pertence às Work Orders que implementarem esses fluxos de gestão de usuários/perfis (ex.: uma futura O1.4.4 ou extensão de `administration/users`), que deverão importar e chamar o mesmo método de domínio, nunca duplicar a lógica.

## 15. API proposta

| Endpoint | Autenticação | CSRF | Rate limiting | Enumeration protection | Auditoria |
|---|---|---|---|---|---|
| `GET /bootstrap/estado` | `AllowAnonymous` | Não aplicável (GET, sem efeito colateral) | Não crítico (leitura pública de baixo risco); pode reaproveitar limite genérico de IP se já existir | Resposta booleana simples, sem detalhe de configuração | "Bootstrap consultado" |
| `POST /bootstrap/iniciar` | `AllowAnonymous` | `CsrfHeaderFilter` (reaproveitado) | Política própria, mais restritiva que `otp-request` (ex.: 3/15min por IP e por e-mail — seção 16 do Security Design) | Resposta idêntica para secret inválido / e-mail não autorizado / `Concluido=true` tratado como 404 antes de chegar aqui | "Tentativa de Bootstrap iniciada", "Secret inválido", "Identidade não autorizada" |
| `POST /bootstrap/otp/verificar` | `AllowAnonymous` | `CsrfHeaderFilter` | Reaproveita `otp-verify` (10/15min) | Mensagem genérica de OTP inválido/expirado, mesmo padrão de `/auth/otp/verify` | "OTP validado (Bootstrap)" |
| `POST /bootstrap/concluir` | `BootstrapAuthenticated` | `CsrfHeaderFilter` | Limite adicional (ex.: 3 tentativas por `BootstrapSessao`) para conter tentativas de força bruta sobre validação de payload | Não aplicável (já autenticado por sessão de uso único) | "Criação da Unidade de Negócio (via Bootstrap)", "Criação/vínculo do Administrador Sênior", "Bootstrap concluído" |

**Request/Response (esquema, não contrato final):**

- `POST /bootstrap/iniciar` — Request: `{ email: string, secret: string }` (secret em corpo, nunca query string, reaproveitando o padrão de `CsrfHeaderFilter` no header separado). Response: `{ message: string }` genérica, idêntica em qualquer caso de rejeição.
- `POST /bootstrap/otp/verificar` — Request: `{ email: string, codigo: string }`. Response de sucesso: `204 No Content` + cookie `mc_bootstrap_sid`; response de erro: mesmo formato genérico já usado em `/auth/otp/verify`.
- `POST /bootstrap/concluir` — Request: `{ unidadeNegocio: { nome, slug } | { id }, administrador: { nome } }` (e-mail não é reenviado — vem da `BootstrapSessao`, seção 13, item 3). Response de sucesso: `{ usuario: { id, email, nome }, unidadeNegocioId } }`; nenhum dado de sessão normal é retornado aqui (o Bootstrap não faz login automático do Administrador recém-criado — ele usa o fluxo normal de `/auth/otp/request` depois, seção 7).

**Efeitos colaterais:** cada endpoint documentado acima já lista os efeitos (emissão de OTP, criação de `BootstrapSessao`, criação de `UnidadeNegocio`/`Usuario`/`Perfil`/`UsuarioPerfil`, encerramento permanente do Bootstrap) — nenhum efeito colateral implícito não documentado é aceitável na implementação real.

## 18. Plano de testes obrigatório

Categorias mínimas (cada uma deve ter ao menos um teste automatizado na implementação real):

1. Bootstrap disponível inicialmente (`Concluido=false` por seed).
2. Secret inválido — rejeitado, resposta genérica.
3. Identidade não autorizada — rejeitado, mesma resposta genérica do item 2.
4. OTP inválido.
5. OTP expirado.
6. OTP replay (reuso do mesmo código após sucesso).
7. Rate limiting (secret, e-mail, IP, e o limite específico de `/bootstrap/concluir` por `BootstrapSessao`).
8. Sessão Bootstrap com privilégios limitados — não acessa nenhum endpoint de negócio existente (`/fornecedores`, `/auth/me`, etc.).
9. Sessão Bootstrap não é aceita por endpoints normais mesmo com claim de autenticação presente (teste negativo direto de `BootstrapAuthenticated` vs. `FallbackPolicy`).
10. Sessão normal (`SessionCookie`) não conclui Bootstrap — teste negativo garantindo que os dois esquemas não se substituem.
11. Conclusão válida — cenário de sucesso ponta a ponta (unitário com fakes, mesmo padrão de O1.4.2).
12. Conclusão concorrente — `Task.WhenAll` com múltiplas instâncias de `DbContext` disputando `/bootstrap/concluir` (mesmo padrão de O1.4.2.1 §18.5); exatamente uma conclui.
13. Segunda execução (após `Concluido=true`) — `/bootstrap/iniciar` retorna 404.
14. Restart — `Concluido=true` persiste após reinício simulado do processo (teste de integração com host real, mesmo padrão de "fail-closed real" de O1.4.2.1 §18.5).
15. Último Administrador Sênior — teste do método de domínio da seção 14 isoladamente (mesmo sem os fluxos de inativação/remoção implementados, testar a lógica pura de "restaria zero administradores? rejeitar").
16. CSRF — `CsrfHeaderFilter` aplicado e testado em `/bootstrap/iniciar`, `/bootstrap/otp/verificar`, `/bootstrap/concluir`.
17. Auditoria — todos os eventos da seção 15/17 gerados nos testes de integração do fluxo completo.
18. Fail-closed — `BootstrapSecretOptions`/`BootstrapAllowedCandidatesOptions` ausentes/vazias tratadas com segurança (nunca "sem restrição").
19. `DevelopmentHeaderAuthenticationHandler` — teste negativo confirmando que este handler não autentica nenhum endpoint de Bootstrap (Bootstrap usa exclusivamente `BootstrapSession`, nunca o esquema de Development, mesmo em Development).
20. Ausência do secret — comportamento de fail-closed descrito na seção 9.
21. Allowlist vazia — comportamento descrito na seção 10.
22. Rollback da transação — falha simulada em qualquer etapa intermediária do `ConcluirBootstrapUseCase` (ex.: exceção ao criar `UsuarioPerfil`) não deixa `Usuario`/`UnidadeNegocio` órfão.

## 23.1. Findings consolidados (aceitos pelo Product Owner em 10/08/2026)

**MEDIUM (não bloqueante para O1.4.3; MEDIUM 1 e 2 bloqueiam promoção para Homologação):**

1. `Cache-Control: no-store` ausente em todas as respostas de `/bootstrap/*` (Security Design §3.4) — hoje inerte (`Concluido=true`), mas bloqueia qualquer novo ambiente. **Bloqueia Homologação.**
2. Bootstrap Secret sem validação de entropia mínima; o valor real configurado é uma frase memorável, não um valor CSPRNG de alta entropia (Security Design §20.4). **Bloqueia Homologação.**
3. Possibilidade de DoS contra um candidato legítimo: o throttle por e-mail é consumido antes da validação do Bootstrap Secret, permitindo que um atacante sem o secret trave o candidato correto.
4. Fallback de CORS não condicionado explicitamente a `IsDevelopment()`, combinado com `AllowCredentials()`+`AllowAnyHeader()` (Security Design §3.6).

**LOW (não bloqueante):**

5. Detecção de violação de índice único por substring de mensagem de exceção, em vez de código estruturado do SQL Server (`SqlException.Number`) — robustez, sem impacto de segurança/integridade.
6. Gap de teste: o ramo `DuplicateRecordException`/detecção de índice único não tem cobertura permanente dedicada (o teste de concorrência existente passa pelo CAS de `RowVersion`, não pelo índice único, que o provider InMemory não aplica); invariante garantida estruturalmente pelo índice real no banco.
7. `BootstrapSessao` não revogada em falha definitiva de `/bootstrap/concluir` (permanece reutilizável dentro dos 15 min de validade).
8. Allowlist não revalidada no momento da conclusão (apenas na emissão do OTP).
9. Rate limit de `/bootstrap/concluir` particionado por IP, não por `BootstrapSessao` (divergência do desenho original desta Work Order, seção 15).
10. `GET /bootstrap/estado` sem rate limiting (endpoint anônimo, booleano puro, sem vazamento de informação).

**INFORMATIONAL (observações técnicas, não convertidas automaticamente em tarefas):**

- Invariante do último Administrador Sênior ainda sem enforcement por contagem real — hoje sem risco por ausência de qualquer caminho de mutação de usuário/perfil/vínculo; deve ser revisitado quando a Gestão de Usuários/Perfis for implementada.
- `DevelopmentRequestIdentity` depende de barreira externa de loopback (do `DevelopmentHeaderAuthenticationHandler`), não de checagem própria — sem exposição real hoje, mas acoplamento implícito.
- Topologia de proxy: `UseForwardedHeaders()` não está registrado; deve constar como pré-condição de deploy no Authentication Infra Readiness Gate (§17.7).
- Estado pós-Bootstrap não foi verificado empiricamente no banco pelo revisor independente (leitura direta bloqueada pelo sandbox) — verificação feita por código/teste, não por consulta direta ao `MaisComprasConnection`.
- Índice único filtrado `IX_CodigosVerificacaoOtp_EmailCandidato_Pendente` não validado em provider relacional real (InMemory não avalia `HasFilter`) — pendência já herdada de O1.4.2, agora estendida a este índice; obrigatória antes de Homologação.

## 25. Riscos

- Divergência entre o wizard de 3 passos já especificado em `ComprasFuncional.md`/`ComprasUX.md` e o passo 0 de segurança introduzido por esta Work Order pode gerar retrabalho de UX se não for comunicada ao time de produto antes da implementação do frontend (O1.4.3.3).
- A decisão de estender `CodigoVerificacaoOtp` para aceitar candidatos sem `Usuario` (seção 11) tem impacto sobre um componente já usado pelo login normal — exige revisão cuidadosa para não introduzir regressão na O1.4.2 já concluída.
- O mecanismo de linha única de `BootstrapEstado` por chave fixa depende de disciplina de código (sempre referenciar o `Id` fixo) — um novo desenvolvedor que não conheça essa convenção poderia inadvertidamente criar uma segunda linha via `Add()` sem checar a chave.
- Rollback de banco/restore de backup antigo pode reabrir o Bootstrap tecnicamente (risco residual já aceito no Security Design, seção 20.20 de `security-design-auth-o1.4.md`) — mitigação é operacional (runbook), não desta Work Order.
